# Thesis experiment plan: 5–11 October 2026

Source: `Thesis_Abhijeet-3.pdf`, Section 4, printed pages 12–23. The PDF is the reference for this plan; `Thesis-proposal.tex` does not contain all its additions. This is a proposed protocol and schedule, not a record of completed experiments. No training or inference was launched while preparing it.

## Recommended scope

Prioritize a reproducible RQ1 baseline and learning curve this week. Prepare RQ2 and perform the available RQ3 analysis alongside training. Run the final test only when the protocol and model are frozen; Friday is not a reason to test an unfinished configuration.

The schedule assumes GPU access and Monday–Friday work, with the weekend as optional overflow. Actual training throughput must be measured before promising completion of every training size.

## Decisions and checks before research runs

1. **Freeze data splits and label provenance.** The PDF states 1,660 source rows, 100 human validation rows and 150 test rows. Existing project notes report 1,658 source rows and flag 166 rows in `final_test.xlsx`; verify actual membership and prior training exposure. Check duplicate pairs and shared questions across all splits. The prepared package reports no exact train/validation pair overlap but 42 shared questions. Do not describe this as question-disjoint evaluation. Audit test IDs and exposure without inspecting test labels or using test performance for development.
2. **Resolve question representation.** Section 4.1 says original Hindi is used, but Section 4.1.5 describes sanitized questions for teacher annotation. Choose and document the primary representation for teacher, training and validation. Keep a raw-versus-sanitized comparison separate if both aligned versions are available.
3. **Train and evaluate both dimensions.** The methodology requires Accuracy and Context & Relevance. The prepared September 25 package trains Accuracy only. Extend it or explicitly treat it as an Accuracy-only pilot; it cannot establish the complete Virtual Moderator.
4. **Verify teacher labels.** Freeze exact teacher model/version, rubric and annotation prompts. Check both label columns and class counts, and review a sample covering all classes. The package README and manifest disagree about label provenance; resolve this from the underlying columns and annotation records before claiming a Claude-supervised experiment. Teacher agreement is not human ground truth.
5. **Freeze one training configuration.** PDF Table 1 specifies 4-bit NF4, double quantization, rank 8, alpha 16, dropout 0.05, attention projection adapters, sequence length 256, answer cap 120 tokens, batch 6, accumulation 4, learning rate 2e-4, two epochs, warm-up 0.05, weight decay 0.01, gradient clipping 1, Paged AdamW 8-bit and seed 42. It describes class-weighted target-only loss. The prepared package instead uses full inputs, batch 1, learning rate 1e-5, one epoch and oversampling. These are separate configurations. Start with a smoke check of the PDF configuration and document any necessary changes before the main curve. Preserve rubric, question and JSON target during truncation; log examples that cannot fit.
6. **Specify selection and evaluation rules.** Report macro-F1 separately for both dimensions. A proposed selection rule is their unweighted mean, with JSON validity and lower resource usage as tie-breakers. This rule is an addition to the PDF and must be fixed before comparison. Reconcile the PDF's validation-loss checkpoint selection with macro-F1 model selection: choose the checkpoint by validation loss within each run, then compare those checkpoints using the fixed model-selection rule.

### Important design details

- **E1 scope:** audit existing candidate results first. The PDF lists broad model families and both local and cloud models; freeze a finite list of exact identifiers rather than running every family variant. Gemma 3 4B is the primary student specified in the PDF. One competitive local alternative and a larger reference can be sufficient for new runs if the existing wider benchmark is reproducible.
- **E2:** tail-only truncation can remove the question and rubric. The primary comparison now varies truncation during both training and validation. A separate inference-only tail/full-input control is optional. Freeze the selected preprocessing before the learning curve.
- **E5:** recommended primary curve trains a fresh adapter from the same base at each cumulative size. This isolates data amount from prior adapter history. If continuing the previous adapter instead, record cumulative optimizer updates and exposure; that measures a sequential adaptation trajectory. The PDF does not resolve this choice. Use nested, category-aware shuffled subsets and inspect class coverage; never manufacture a missing class.
- **E6:** weighting must affect example contributions before batch reduction. Verify that normalization does not cancel the weights, especially at batch size one. Specify how weights are defined for each dimension if using one JSON output containing both labels.
- **Repetitions:** three inference runs assess decoding stability, not training variability. If time permits, retrain the selected development configuration with seeds 42, 43 and 44 before final testing; treat this as additional robustness evidence.
- **Metrics:** macro-F1 averages only classes 0,1,2. Invalid predictions remain failures for the true class and are reported separately; never add -1 as a fourth scored class or discard failures. Report the severe error of true Accuracy=0 predicted as 2 with its denominator.
- **E7:** test labels must come from experts to support a human-alignment claim. If only teacher labels exist, name the result teacher agreement. Resample or swap shared-question/user groups together. Predefine the primary inference run or aggregation rule and the Holm comparison family before revealing test results. Do not treat repeated predictions of the same example as independent observations.
- **E8:** the PDF names Claude, Gemini, ChatGPT Astra and Qwen32B, without exact reproducible identifiers. Confirm accessible versions before execution. If the intended conclusion is local SLM suitability, include locally deployable candidates and identify larger/cloud systems as references. Moderator ratings are proxy quality measures, not proven factual correctness. Review a fixed balanced sample with experts where feasible; the moderator has not automatically been validated on new generators' answer distributions. Report unavailable cloud memory as unavailable rather than estimated local measurements.
- **E9:** the dataset section says Correct/Minor Error/Incorrect labels describe Sarvam answers; the methodology sometimes treats them as moderator-decision labels. These are different outcomes. Existing labels alone support answer-quality error analysis, not moderator accuracy. User/category comparisons require denominators; error counts alone cannot establish that one group performs worse. Multiple error causes can sum to more than 100%. Existing draft counts 109/16/15 out of 140 correspond to 77.9%/11.4%/10.7%; its last two percentages are reversed. User-level variation alone does not establish speech clarity as the cause.

## Results to save for every run

Save experiment ID, exact model revision, adapter provenance, data IDs/hashes, label source, input column mapping, prompt text/hash, truncation policy, training and decoding settings, seed, hardware/software versions, timing and memory, raw outputs, parsed predictions, validity flags and both dimensions' metrics. Store training class counts and unique rows separately from any repeated training presentations.

Minimum successful week: a trustworthy two-dimension baseline, fixed prompt/input policy, the N=0–500 curve, one balancing control, and the RQ3 descriptive tables. Final-test statistics and a full RQ2 ranking follow only when their dependencies are satisfied.
